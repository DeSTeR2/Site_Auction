# 05. Оновлення в реальному часі

Як сторінка лота без перезавантаження бачить нові ставки, лідерство і завершення торгів (`project.md` §9.4.3, §9.4.4) з затримкою не більше 2 секунд.

## 1. Транспорт

- ASP.NET Core SignalR, хаб `AuctionHub` за адресою `/hubs/auction`.
- Транспорти: WebSocket, запасний — Server-Sent Events / long polling (вирішує клієнт SignalR).
- Хаб відкритий для гостей: сторінку лота з таймером і ціною бачать усі (§5.1).
- Два екземпляри застосунку за Caddy зʼєднані **Redis-бекплейном** (`ConnectionStrings:Redis`, префікс каналів `auction`). Повідомлення, надіслане в групу на одному екземплярі, отримують клієнти, підключені до іншого.
- Без `ConnectionStrings:Redis` (локальний запуск, тести) хаб працює без бекплейна на одному екземплярі.

## 2. Три канали

| Канал | Група SignalR | Хто в ній | Що отримує |
|---|---|---|---|
| Публічний стан лота | `lot:{lotId}` | Усі, хто відкрив сторінку лота | Ціна, мінімальна ставка, лічильники, новий рядок історії з замаскованим нікнеймом, завершення |
| Особистий | `user:{userId}` | Усі вкладки користувача, що увійшов | «Ви лідер» / «Вашу ставку перебито», лічильник непрочитаних сповіщень |
| Продавець і адміністратор | `lot:{lotId}:owner` | Продавець лота й адміністратор на сторінці лота | Те саме, що публічний, але з повними нікнеймами (§8.7) |

- `JoinLot(lotId)` / `LeaveLot(lotId)` додають підключення в `lot:{lotId}`; якщо користувач — продавець цього лота або адміністратор, ще й у `lot:{lotId}:owner`. Права перевіряє сервер, не клієнт.
- У `user:{userId}` підключення потрапляє автоматично в `OnConnectedAsync` за сесійним cookie.

## 3. Повідомлення

Сервер шле **знімок стану**, а не дельту. Так клієнту не треба зберігати порядок повідомлень, а пропущене повідомлення виправляється наступним.

```json
{
  "lotId": 42,
  "version": 7,
  "status": "active",
  "currentPrice": 650,
  "minimumBid": 700,
  "bidCount": 7,
  "bidderCount": 3,
  "endsAt": "2026-12-01T18:00:00Z",
  "lastBid": { "bidder": "o***a", "amount": 650, "placedAt": "2026-12-01T17:41:12Z" },
  "result": null
}
```

| Подія хаба | Канал | Коли |
|---|---|---|
| `LotStateChanged` | `lot:{id}`, `lot:{id}:owner` | Після COMMIT прийнятої ставки, приховування, повернення, завершення |
| `LeadershipChanged` | `user:{id}` | Новий лідер і попередній лідер після прийнятої ставки |
| `UnreadCountChanged` | `user:{id}` | Після створення сповіщення |

- `version` = `bid_count` лота. Клієнт ігнорує знімок з меншою версією, ніж уже показаний.
- Публікує `ILiveLotPublisher.PublishStateAsync(lotId)` з обробника `IAfterCommitHandler`. Він читає знімок уже після COMMIT, тому ніколи не покаже ставку, яку потім відкотили.

## 4. Перепідключення

- Клієнт SignalR перепідключається автоматично.
- Після `onreconnected` клієнт знову викликає `JoinLot` і запитує `GET /api/lots/{id}/state` — той самий знімок, що й у `LotStateChanged`. Так сторінка показує актуальний стан навіть після довгого розриву (§9.4.3).

## 5. Таймер

- Таймер рахує клієнт від `endsAt` з поправкою на різницю годинників: при завантаженні сторінки сервер повертає свій час, клієнт зберігає зсув.
- Коли таймер дійшов до нуля, клієнт показує «Торги завершено», але результат (переможець, фінальна ціна) показує лише після `LotStateChanged` зі `status = sold | unsold` від сервера.

## 6. Затримка

Бюджет 2 секунди від COMMIT до показу в іншого учасника:

| Етап | Очікувано |
|---|---|
| Обробник після COMMIT → читання знімка | < 50 мс |
| Redis-бекплейн між екземплярами | < 10 мс |
| Доставка WebSocket | < 100 мс |

Вимірюється в прототипі (SITE-55): сервер ставить у знімок час COMMIT, клієнт рахує різницю.

## 7. Питання до прототипу (SITE-55)

1. Чи доходять повідомлення клієнтам на `app-2`, коли ставку прийняв `app-1` (перевірка бекплейна за Caddy)?
2. Чи тримає Caddy WebSocket-зʼєднання з `round_robin` без «липких» сесій, або потрібен `lb_policy cookie`?
3. Яка реальна затримка p95 від COMMIT до показу при 100 одночасних ставках?
4. Чи вистачає знімка в `LotStateChanged` для історії ставок, чи треба окреме повідомлення з рядком історії?
5. Що робити, якщо Redis недоступний: падати на старті чи працювати без бекплейна з попередженням у логах?
